# 07 · 平台差异与结论迁移

> 同一份代码、同一个矩阵，在 RTX 3060 上 fp32 因子给 1.34×，在沐曦 X201 上给 1.02×。
> 这篇讲清楚：为什么，以及哪些结论能搬、哪些不能。

---

## 1. 两个平台的关键差异

| 项 | RTX 3060（开发/代理平台） | Mars X201（目标平台） |
|---|---|---|
| 架构 | sm_86，GA106 | HT-core 1000，104 SM |
| HBM 峰值带宽 | ~360 GB/s | **~1843 GB/s**（5 倍） |
| FP64 能力 | 1:64 精简（游戏卡） | **原生完整** |
| warp 宽度 | 32 | **64** |
| 共享内存/SM | 100 KB（可配） | 65536 B |
| 软件栈 | CUDA 12.6 + nvcc | HPCC 3.5.3 + `cucc`（CUDA 兼容层） |
| 混合精度结论 | 分解 1.34× / 三角 1.30× / SpMV 1.35–2.81× | 分解 **1.02×** / 三角 **1.01×** |

---

## 2. 为什么收益消失

混合精度的全部收益来自一个前提：**内核是带宽受限的**。

```
带宽受限 → 每非零元搬运字节数减半 → 同样带宽下可处理的数据量翻倍 → 时间减半
```
AI ≈ 0.2 FLOP/Byte 的稀疏内核在 3060（平衡点 ~15–60）上正是这种状态，所以成立。

在 X201 上这个前提被两个因素破坏：

1. **带宽太充裕**。1843 GB/s 对 AI≈0.2 的内核来说过剩，字节减半不再是瓶颈所在。
2. **该内核在 X201 上是延迟受限，不是带宽受限**。依据：单线程分解耗时
   21.9 s（n=4050），而同一矩阵在 3060 上只需数百毫秒量级。差两个数量级说明
   远未跑满吞吐——时间花在**等 gather/scatter 的每次访存返回**，而不是搬字节。
   等待次数由非零元个数决定，与非零元占几个字节无关。

**推论**：在 X201 上想从精度上拿收益，得先让内核变成带宽受限——
也就是先并行化（实测 29.9×），把延迟藏起来。顺序反了就没收益。

---

## 3. 结论适用边界（引用前先查这张表）

| 结论 | 3060 | X201 | 可否跨平台引用 |
|---|---|---|---|
| fp32 因子内存减半 | ✅ 2.13× | ✅ 1.50×（值口径 2×） | **可以**（纯容量，与带宽无关） |
| fp32 因子分解加速 | ✅ 1.34× | ❌ 1.02× | **不可以** |
| 三角求解加速 | ✅ 1.30× | ❌ 1.01× | **不可以** |
| SpMV fp32 大矩阵加速 | ✅ 1.35–2.81× | 未测 | **不可以**（未验证） |
| 并行化收益 | 12–22× | ✅ 29.9× | 可以（方向一致，幅度不同） |
| 分解质量不退化 | ✅（flash-adc 除外） | ✅ nnz 完全一致 | 可以（但需逐矩阵验） |
| 精度路径需动态升级 | ✅ 12/33 仅 fp32 可行 | 未测 IR 全链 | **部分**（机理通用，数字不通用） |

**一句话规则**：凡是**与容量有关**的（内存、布局、复用）可以搬；
凡是**与时间/带宽有关**的，必须在目标平台上重测。

---

## 4. 这组数据本身的边界

诚实声明，避免被过度引用：

- **只有一个矩阵**（pg2k，n=4050）。没有 flash-adc / rajat / pg5k 的对照。
- **只覆盖两段**（分解、三角求解）。SpMV 与 GMRES-IR 端到端没在 X201 上测。
- **CV 2.05%**，按实验脚本自定口径只能报区间 `[0.97, 1.04]`，不能报单点数。
- 8 次有效运行，跨 3 张卡（GPU 0/2/3），结论在卡间一致——这一点是可靠的。

---

## 5. 下一步该测什么（按价值排序）

1. **SpMV fp32 vs fp64 @ X201**。这是 3060 上收益最大的一段（1.35–2.81×），
   也最可能受带宽过剩影响。测了才知道 SpMV 是否和 LU 一样归零。
2. **GMRES-IR 端到端**。用户真正感知的是"解一次方程组要多久"，
   而不是某个内核快多少。全链路口径下 fp32 的账面收益会被 fp64 残差抵消多少，目前未知。
3. **换大矩阵（pg100k / rajat22）**。pg2k 的 ST 分解 21.9 s 里启动/收尾占比可能不小；
   规模上去后延迟受限的特征是否改变，决定 §2 的解释成立到哪一档。
4. **采带宽计数器**。X201 有 `ht-smi` / `htSmlGetDieHbmBandWidth`，可以直接证伪或证实
   §2 的"延迟受限"推断——目前它只是推断。

---

## 6. 一句话总结

> 在 3060 上，混合精度是"省带宽换速度"；在 X201 上，带宽不缺，缺的是并行度。
> **同一份代码，两个平台的最优策略相反。** 这不是代码的问题，是瓶颈位置变了。
